# POSO Violation Monitoring System

Public Order and Safety Office, Municipality of Luna, Apayao.

The system records traffic, peace and order, public safety, and other local ordinance violations. Treasury collects payments and issues official receipts. POSO verifies those receipts and retains the incident and settlement history for reporting.

## Access and workflow

| User | Responsibilities |
| --- | --- |
| Enforcer | Enter required name, address, offense and confiscated-ID type; optionally record a plate and additional information. Preview and confirm. Review only their own submissions and provide or replace citizen access codes. |
| Admin | Monitor records, verify Treasury settlements, reconcile an unknown fine with ordinance evidence, reverse a mistaken verification with a reason, manage staff and offense versions, and run reports. Admins cannot enter, freely edit, or delete incident records. |
| Citizen | Enter the full name on a record and its private code to check one settlement status without a staff account. |

Only Admin and Enforcer are staff roles. The old Officer role and Citations interface are retired. Internal `citations` rows retain payment allocations; they are not Treasury receipts generated by this system.

Citizens see **Not Yet Verified**, **Settled**, or **Dismissed**. Not Yet Verified means POSO has not confirmed a Treasury payment; the citizen may already have paid. A viewing session lasts 15 minutes. The private code remains valid until staff replace it; replacing it also revokes existing access grants.

Admin verification requires Treasury receipt number, receipt date, receipt total, and confirmation of inspection. The system records the admin and verification timestamp automatically. Treasury date and POSO date are distinct. Receipt sharing is checked against the same person, total, date, and remaining allocated value. Unknown historical dates remain unknown.

## Stack

- PHP 8.3+, Laravel 13, MySQL 8.
- Blade templates and locally served Bootstrap 5.3.0, Bootstrap Icons 1.11.0, fonts and application CSS.
- File sessions by default locally, with credential-version revocation on password, role, or activation changes.
- PHPUnit with isolated SQLite databases for application regression tests. MySQL checks remain necessary for migration and concurrency behavior.

This is one application with separate role interfaces and a restricted citizen hostname. It has no automatic Treasury integration.

## Local setup

1. Use PHP 8.3 or newer. Install dependencies with `composer install`.
2. Copy `.env.example` to `.env`, run `php artisan key:generate`, and configure `DB_CONNECTION=mysql`, database/host/user/password, `APP_URL`, and `CITIZEN_DOMAIN`.
3. Create an empty database, then run `php artisan migrate`. Back up an existing database before migration. Do not run `migrate:fresh` against it.
4. Run `npm run build` with Node 24 to validate local asset references. No frontend dependency installation or Vite server is needed for these Blade pages.
5. Start Apache/MySQL in Laragon, or run `php artisan serve` for the application. See [local host setup](ops/laragon/README.md).

For a fresh demonstration database only, `php artisan db:seed` creates demo accounts and profiles. The seeder refuses production environments. Demo account passwords are unsuitable for deployment; change them before any public access. New or reset passwords require 15–128 characters. Existing credentials remain unchanged by migrations.

## Verification

Set `APP_ENV=testing`, `DB_CONNECTION=sqlite`, `DB_DATABASE=:memory:`, and an empty `DB_URL`, then run `php vendor/phpunit/phpunit/phpunit`. Enable `pdo_sqlite` and `sqlite3` in the selected PHP executable. `Tests/TestCase.php` refuses another database before refresh/reset traits run. Never bypass that safeguard to test against an existing MySQL database.

Run `npm run build` for asset checks. CI performs both checks on pushes and pull requests once the repository is hosted on GitHub.

## Reporting and preservation

Daily, weekly and monthly reports separate apprehensions, settlements verified during the period, and verification changes. Current status may differ from its historical status at the period end. The page shows 50 rows per section with independent pagination; printing includes the displayed rows. Download CSV for all period rows. Export streams records in batches and neutralizes formula-like text.

Incident snapshots preserve names and addresses at recording time. Offense changes create versions with a stable identity, preserving issued wording and fines. Existing version lineage is not guessed during migration. The database enforces one payment allocation per violation, unique receipt references, and unique submission tokens.

Name suggestions use a normalized prefix and score at most 200 candidates, displaying up to 20. They are suggestions, not proof of identity or an exhaustive person search. New-person confirmation remains explicit. Prepared drafts are kept separately for up to 30 minutes, with at most ten open previews. Opening the form does not clear them; Clear drafts does.

## Operations

Run `php artisan poso:backup` to create a consistent MySQL dump in `storage/app/private/backups`. Set `POSO_MYSQLDUMP` if the executable is elsewhere. A daily 23:00 backup is registered with Laravel's scheduler; the host must invoke `php artisan schedule:run` every minute for it to execute. See [deployment and recovery](ops/operations.md).

The 15-day due date, incident-date policy, any dismissal/correction authority, and confiscated-ID release procedure need office-approved rules. The fixes do not invent those authorities or add a Treasury payment gateway.
