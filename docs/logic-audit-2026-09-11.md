# POSO system logic audit — 11 September 2026
**Resolution update — 11 September 2026:** The ten implementation findings below have been addressed. The original findings are retained as audit evidence. See [the remediation record](audit-fixes-2026-09-11.md) for the resulting behavior, validation, and historical-data limits. The business-rule questions listed separately are not claims about applicable ordinances.

Reviewed against the intended workflow: Enforcers record violations; Treasury collects payments and issues official receipts; Admins verify Treasury receipts and monitor retained records and reports. The application has useful authorization and confirmation controls, but the remaining findings below prevent treating its identity matching, public access, and analytics as reliable for operational use.

This was a source-code and automated workflow review, with an independent read-only review of the main findings. It was not a production penetration test or a legal review. Concurrency was inspected in code, not load-tested.

**Completed during this audit, following your instruction**

The Officer role was retired from account forms, validation, access rules, and database choices. Existing Officer accounts were converted to Enforcer. Legacy record-editing and deletion endpoints now reject requests from both roles. The migration logs the conversion and preserves user IDs and record authorship. Existing usernames and passwords are unchanged.

Local database verification: roles changed from 1 Admin / 2 Officers / 2 Enforcers to 1 Admin / 4 Enforcers. Counts remained 5 users, 6 violators, 1 violation, and 1 payment record. A hash of all violation IDs and their recording-user IDs was identical before and after conversion. Migration status confirms the conversion ran in batch 4.

Before retirement, isolated probes showed officers could transfer a paid violation to another person/offense without changing its verified receipt or fine; delete a paid violation so reports lost it while dashboard payment totals retained it; and delete a profile so the violation list returned HTTP 500. Role retirement closes those public application paths. It does not repair any already altered/deleted historical data; no historical-data cleanup was performed.

**Remaining findings, ordered by priority**

1. **High — Different people with the same name are automatically merged.** An exact name selects the first matching profile before checking the request to create a new person. Even `confirm_new=1` cannot create a separate exact-name person; confirmation also rejects a new matching name. Reproduction: entering another Juan Dela Cruz at a different address produced one profile with two violations. This can put someone else's violations and payment history on a person. Use explicit identity confirmation with additional distinguishing details, allow legitimate same-name people, and never treat a name as a unique identifier. Sources: [ViolationController.php](../app/Http/Controllers/ViolationController.php), lines 91–95 and 167.

2. **High — New entries rewrite details used by historical records.** Confirmation overwrites the shared violator profile. Address and plate are read from that current profile for previous records; a blank plate also inherits the previous plate. Reproduction: a second entry changed the first violation's displayed address and plate. Even when it is the same person, a later address or vehicle should not rewrite the circumstances of an older incident. Store incident-specific snapshots, separate from the person's current profile. Sources: [ViolationController.php](../app/Http/Controllers/ViolationController.php), lines 115–118 and 177–180; [period.blade.php](../resources/views/reports/period.blade.php), line 13.

3. **High — Anonymous users can enumerate personal record histories.** Public numeric-ID URLs require no proof that the requester is the subject. Public results expose name, address, apprehension dates, and payment status. Searching for `%%%` satisfies the three-character check and matches arbitrary names because SQL LIKE wildcards are unescaped. Both routes were reproduced without authentication. Rate limiting limits speed, not access. The public interface deliberately hides offense descriptions, fines, license/contact details, and birthdate; the concern is the remaining disclosure and broad enumeration. Require a suitable identity/reference check, minimize displayed details, and escape wildcard input. Exact names or unpredictable URLs alone are not identity verification. Sources: [SearchController.php](../app/Http/Controllers/SearchController.php), lines 21–30 and 42–44; [public result](../resources/views/search/_violator_result.blade.php), lines 1–8.

4. **Medium — One receipt reference can settle unrelated people's records without review.** The server checks a receipt string and confirmation checkbox only. Reproduction: the same receipt number settled two separate people's violations. One Treasury receipt might legitimately cover multiple offenses, so a simple unique constraint is not automatically the right fix. Define how receipts are allocated, display existing uses for review, and associate verification with the covered person/violations and amount. Source: [CitationController.php](../app/Http/Controllers/CitationController.php), lines 30–44.

5. **Medium — “Unpaid violations” excludes overdue violations.** The displayed value counts only `pending` payment records. Reproduction: a single unpaid record became overdue and the unpaid statistic showed zero while the overdue statistic showed one. Count pending and overdue together using the same eligibility rules as the violation list. Sources: [DashboardController.php](../app/Http/Controllers/DashboardController.php), line 24; [dashboard](../resources/views/dashboard/index.blade.php), line 86.

6. **Medium — Amending an offense removes its historical records from the dashboard ranking.** Used offense types are correctly retired and versioned to preserve historical wording. However, the ranking only includes current types. Reproduction: amending the sole recorded offense left total violations at one but displayed “No offense data yet” in the ranking. Include historical versions or aggregate them under a stable offense identity. Sources: [DashboardController.php](../app/Http/Controllers/DashboardController.php), line 42; [AdminController.php](../app/Http/Controllers/AdminController.php), lines 104–109; [dashboard](../resources/views/dashboard/index.blade.php), lines 90–93.

7. **Medium — Historical dismissed violations are still treated as unpaid and can become overdue.** Payment queries check paid status without excluding dismissed violations. A fixture representing an existing dismissed record was counted as active/unpaid and became overdue. The public page and reports also render every non-paid record as “Unpaid.” No current role can dismiss records after retirement, but existing dismissed data still needs a coherent policy. Define dismissed/voided outcomes independently from payment status and apply the same rules to every view and statistic. Sources: [Violator.php](../app/Models/Violator.php), lines 27–30; [Citation.php](../app/Models/Citation.php), lines 27–31; [report](../resources/views/reports/period.blade.php), line 13.

8. **Medium — All offenses are still categorized as traffic violations by the admin forms.** Both add and edit submit the hidden category `Traffic Violation`. The app can accept a general offense name, but public-order or safety offenses are mislabeled in stored data. Add supported categories and preserve the selected category during edits. Confirm the actual ordinance catalog with POSO; this audit does not establish which ordinances apply. Source: [violation_types.blade.php](../resources/views/admin/violation_types.blade.php), lines 65 and 99.

9. **Medium — A mistaken payment verification has no correction workflow.** A second verification returns early once a record is paid, so an incorrect receipt cannot be corrected and a mistaken paid status cannot be reversed through the app. Duplicate-submit protection is valuable, but it needs a separate authorized correction flow with a reason and preserved audit history. Source: [CitationController.php](../app/Http/Controllers/CitationController.php), lines 37–44. The existing idempotency test confirms that later receipt values are ignored.

10. **Medium, code-based concurrency risk — Internal record numbers can collide.** The removed Citations UI still uses the existing payment-storage model internally. `generateTicketNo()` uses today's row count plus one. Two simultaneous submissions can generate the same unique number, causing one transaction to fail. This was identified in code, not reproduced under concurrent MySQL load. Use a database-generated sequence or other concurrency-safe identifier, with appropriate retry behavior. Internal storage alone is not a failure to remove the Citations interface. Source: [Citation.php](../app/Models/Citation.php), lines 35–39.

**Business rules still to confirm**

- Every violation currently receives a fixed 15-day deadline. Confirm whether this applies to every offense category before using overdue figures operationally.
- `paid_at` records the POSO verification date, as the current interface explicitly states. If reports need the actual Treasury payment date, store that separately rather than replacing verification timestamps.
- Define an authorized correction process for enforcer mistakes and confiscated-ID return tracking. Removing Officer access should not lead to direct database edits as routine work.

**Validation**

The application suite passed: 34 tests, 357 assertions. Six additional isolated audit probes passed: 28 assertions. Those probes intentionally assert that defects are reproducible; their passing result does not mean the defects are fixed. They cover identity merging/history overwrite, public enumeration, receipt reuse, dismissed status, and the two dashboard errors. Probe source: [original defect probes](../tmp/logic-audit/pre-fix-probes.txt). Pre-retirement reproduction source is retained as a text artifact in the same folder.

The role migration was tested with existing linked records using SQLite, then verified against the local MySQL database with unchanged counts and authorship. A test caught SQLite table-rebuild cascade risk; the migration was adjusted before local deployment. At the time of the original audit, the other findings remained open. The resolution update above supersedes that status.

Prioritize identity matching and historical snapshots, then public access, receipt verification/corrections, and consistent payment/report calculations. After those changes, convert the audit probes into tests asserting the corrected behavior.
